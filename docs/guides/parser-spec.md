# 微信导出解析规格

> 目标：直接指导 `core/parser` 实现，将微信「邮件发送聊天记录」导出的 txt 解析为符合 [`../contracts/session.schema.json`](../contracts/session.schema.json) 的 `ChatSession`。

## 1. 概述

DeepTalk 仅导入微信官方「邮件发送聊天记录」导出的纯文本 txt（图片不导入）。本文档定义该导出的格式特征、消息类型识别规则、解析状态机，以及**时间戳缺失时的推断策略**——这是解析器最核心、最易出错的环节。

- 输入：单个 txt 文件（UTF-8，可能带 BOM）。
- 输出：一个 `ChatSession`（单文件 = 单会话），`source = "wechat-email-txt"`。
- 伴生样例：[`wechat-export-samples/`](wechat-export-samples/)。

## 2. 文件结构

一个导出文件由两段组成：

```
{可选元信息头}
{空行}
{消息块流}
```

### 2.1 元信息头（可选）

位于文件首部，直到第一个空行为止。每行形如 `键:值`，已知键（全部可选，缺省不影响解析）：

| 键 | 说明 | 用途 |
|----|------|------|
| `消息记录` | 固定标题行 | 标识文件类型 |
| `消息发起人` | 本机账号昵称 | **辅助判定 `me`**（见 §4.2） |
| `聊天对象` | 对方昵称 | 判定 `peer`，并辅助判定 `me` |
| `开始时间` | `YYYY-M-D H:MM:SS` | 首条消息时间戳缺失时的回退值（见 §7.2） |
| `结束时间` | 同上 | 填充 `updated_at` 回退值 |
| `消息条数` | 微信统计值 | **仅供参考，解析器以实际解析条数为准** |

> 解析器**不得**因头字段缺失或 `消息条数` 与实际不符而报错；以实际解析结果重算 `message_count`。

### 2.2 消息块流

头之后为消息块序列。块之间以**单个空行**分隔。每个块 = 「可选时间行 + 一行或多行内容」。详见 §3、§6。

## 3. 时间行格式

时间行是块的「首行」并决定该块是否携带显式时间戳与发送者。

### 3.1 正则

```
^(?<date>\d{4}[-/]\d{1,2}[-/]\d{1,2})\s+(?<time>\d{1,2}:\d{2}(?::\d{2})?|上午\s*\d{1,2}:\d{2}|下午\s*\d{1,2}:\d{2})\s+(?<nick>.+)$
```

匹配成功 → 该块携带显式时间戳，`nick` 为发送者昵称；其后的行（直到块末）为消息内容。

### 3.2 日期 / 时间变体

微信导出因版本与系统 locale 不同存在多种写法，解析器须全部兼容：

- 日期：`2024-3-1`（无前导零，最常见）、`2024-03-01`、`2024/3/1`。
- 时间：`9:30:00`、`09:30:00`、`9:30`（无秒）、`下午 1:05`、`下午1:05`。
- `上午`/`下午`：12 小时制，解析时换算为 24 小时（下午 +12，12 点特例：`下午12:00` = 12:00，`上午12:00` = 0:00）。
- 秒缺失时补 `:00`。

### 3.3 非时间行

块首行不匹配时间行正则时，该块为**无时间行块**：内容即从首行开始，时间戳与发送者按 §7 推断策略补全。

## 4. 昵称与「我」识别

### 4.1 双方昵称

1:1 导出中至多出现两个不同昵称。解析器收集所有显式时间行中出现的 `nick`。

### 4.2 判定 `me`

`sender` 字段中本机账号统一记为 `me`。判定优先级：

1. 若元信息头存在 `消息发起人`，其值即本机昵称 → 映射为 `me`。
2. 否则若存在 `聊天对象`，对方昵称已知；1:1 会话中**另一个**昵称即本机 → `me`。
3. 否则（无头信息）：依赖调用方传入的「本机昵称」配置；若未提供，默认**首个出现**的昵称为 `me`（不可靠，须在 `note` 中标注）。
4. 仅出现一个昵称时：该昵称即对方，所有消息 `sender = peer`，本机未发言。

`peer` 取 `聊天对象`；缺省时取非 `me` 的那个昵称；仅一个昵称时取该昵称。

## 5. 消息类型识别

`type` 枚举：`text` / `voip_text` / `quote` / `system`。

### 5.1 system（系统消息）

无时间行或时间行后的内容行匹配下列模式之一：

```
^.+\s撤回了一条消息$
^.{1,20}\s拍了拍.{0,20}$
^你已添加了.+，现在可以开始聊天了。$
^.+邀请你加入了群聊.+$
^以上是打招呼的内容$
^你通过.+添加了.+$   （等同类系统动作）
```

匹配 → `type=system`，`sender` 取动作主语（如「星河 撤回了一条消息」中的「星河」），`content` 为整行原文。系统消息时间戳常缺失 → 按 §7 推断。

### 5.2 voip_text（语音转文字）

块内容首行为 `[语音]`，且其后（块内、空行前）存在下一行：

- 形如 `已转文字：{transcript}` → `content = transcript`（去前缀）。
- 或直接为转写文本 → `content = 该行`。

→ `type=voip_text`，`content=transcript`，丢弃 `[语音]` 标记行。若 `[语音]` 后无任何转写行 → 退化为 `type=system`，`content="[语音]"`，并在 `note` 记录「无转写文本」。

### 5.3 quote（引用回复）

块内容首行为 `「{quoted}」`（被引文本，可能带 `昵称：` 前缀），其后行为回复正文。

→ `type=quote`，`content=回复正文`，`quote_of` 按 §5.4 解析。

### 5.4 quote_of 解析

在被引文本之前、同一会话内向前查找：取 `content` 与 `quoted` 去引号去前缀后**最接近且包含**的消息 id。规则：

1. 精确匹配优先（去首尾空白与标点）。
2. 其次子串包含（被引文本是某消息内容的子串或反之）。
3. 找不到 → `quote_of` 省略，`note` 记录「引用目标未匹配」。

### 5.5 text（普通文本）

不满足上述任一类型 → `type=text`，`content` 为块内内容行（去除时间行后）按原顺序用 `\n` 拼接，保留多行结构。

## 6. 解析状态机

按行顺序处理，维护上下文：

1. **阶段 A（头解析）**：逐行读入直到首个空行；按 `键:值` 提取头字段。首个空行后进入阶段 B。
2. **阶段 B（块切分）**：以空行为块分隔。连续空行视为单个分隔（不产生空块）。文件尾部可无尾随空行。
3. **阶段 C（块解析）**，对每个块：
   - 取首行尝试时间行正则。
   - **命中**：记录 `last_ts`、`last_sender`；余下行为内容。
   - **未命中**：该块无显式时间行；内容=全部行；时间戳/发送者走 §7 推断。
   - 按优先级判定 `type`：先 `system`（§5.1）→ `voip_text`（§5.2）→ `quote`（§5.3）→ `text`（§5.5）。
   - 多行内容用 `\n` 拼接，去除块末尾空行。
4. **阶段 D（装配）**：生成 `session_id`、`peer`、`created_at`、`messages`、`message_count`、`note` 等。

### 6.1 session_id

建议 `sha1(peer + created_at)` 取前 16 位（与 schema description 一致），保证可复现。

## 7. 时间戳缺失时的推断策略（核心）

微信导出常省略时间行：连续同发言人消息仅首条带时间；系统消息多无时间行；跨天时同一天后续消息可能仅写时间不写日期。所有推断出的时间戳**必须** `inferred_time=true`，并在会话 `note` 汇总推断情况。

### 7.1 日期回填（跨天省略日期）

若时间行仅含时间无日期（罕见变体），或某块推断时间需继承日期：

- 向前回溯到最近一条**携带显式日期**的消息，继承其日期。
- 文件起始处无前导日期 → 使用头 `开始时间` 的日期；仍缺失 → 标记 `inferred_time=true` 并在 `note` 说明「日期未知，采用回退」。

### 7.2 时间戳回填（无时间行块）

对无时间行块，按顺序尝试：

1. **继承前一条**：取最近一条已解析消息的时间戳（`last_ts`），`inferred_time=true`。
2. **前导无前例**（块位于文件首、无前序消息）：使用头 `开始时间`；缺失则用头 `开始时间` 的日期 + `00:00:00`；再缺失则 `created_at` 回退为当前导入时间，并 `inferred_time=true`、`note` 标注「文件起始时间戳缺失，采用回退时间」。
3. **时序冲突**：若继承值导致消息时间早于前一条且发送者非同一人（不可能的回退），保持等于前一条时间（不倒退）。

### 7.3 连续同发言人

对无时间行、且前一条与当前块经内容判定为同一发送者的消息：时间戳 = 前一条时间戳，`inferred_time=true`。这是最常见的省略场景。

### 7.4 inferred_time 默认值

显式时间行的消息 `inferred_time=false`（schema 默认）。仅推断路径置 `true`。

## 8. 字段映射

| txt 来源 | `ChatSession` / `message` 字段 | 说明 |
|----------|-------------------------------|------|
| 头 `聊天对象` / 推断 | `session.peer` | 对方昵称 |
| 头 `开始时间` / 首条消息 | `session.created_at` | ISO 8601（`YYYY-MM-DDTHH:MM:SS+08:00`，按导出 locale 视为东八区） |
| 头 `结束时间` / 末条消息 | `session.updated_at` | 缺省省略 |
| 固定 | `session.source` | `"wechat-email-txt"` |
| `sha1` | `session.session_id` | 见 §6.1 |
| 实际解析 | `session.message_count` | 重算，不用头 `消息条数` |
| 推断汇总 | `session.note` | 时间戳推断情况等 |
| 时间行 `nick` / 推断 | `message.sender` | 本机→`me` |
| 内容行拼接 | `message.content` | `\n` 拼接 |
| §5 判定 | `message.type` | text/voip_text/quote/system |
| 时间行 `date time` / 推断 | `message.timestamp` | ISO 8601 |
| §7 | `message.inferred_time` | bool |
| §5.4 | `message.quote_of` | 仅 quote |
| 会话内自增 | `message.id` | `m{NNN}`（1 起递增） |

> 时区：微信导出为本地时间，统一按 `Asia/Shanghai`(+08:00) 输出带偏移的 ISO 8601。

## 9. 边界与异常处理

- **BOM**：读入时剥离 UTF-8 BOM。
- **CRLF / LF 混用**：统一按 `\n` 归一，`\r` 丢弃。
- **空块 / 空文件**：空块跳过；空文件或仅含头的文件 → 返回 `messages=[]`、`message_count=0`，不报错。
- **无法识别行**：既非时间行又非已知系统模式、且无前序 `last_sender`（文件首块即无时间行且无头）→ `type=text`，`sender=peer`，时间戳走 §7.2。
- **头 `消息条数` 不符**：忽略，以实际为准，`note` 记录差异（可选）。
- **引用目标未匹配**：`quote_of` 省略，`note` 记录。
- **图片 / 表情 / 文件等非文本**：本规格范围外（仅纯文本导入）；若导出含 `[图片]` 等占位行，按 `type=system` 保留原文，不解析内容。
